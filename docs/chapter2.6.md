## 2 第 2 章 嵌入式软件设计模式

> 承接 §2.5 生产者-消费者模式：上一节我们用环形缓冲区（Ring Buffer）将中断服务程序（ISR）与后台任务解耦，解决了"数据何时产生、何时消费"的时序问题。但数据被消费之后应当"做什么"，仍以硬编码的 `if-else` 散落在代码各处。本节在生产者-消费者的数据通道之上，引入**命令模式（Command Pattern）**，为"消费端如何调度动作"给出一种可扩展、低耦合的工程答案，并以一个可在 STM32F103 上运行的串口命令行（Command Line Interface, CLI）贯穿始终。

### 2.6 命令模式

在嵌入式产品的调试、参数整定与现场运维中，一个能通过串口敲入 `led on`、`ver`、`help` 等短命令的交互式接口几乎是标配——它无需上位机软件，一条串口线即可诊断设备。以农业物联网场景为例，田间的土壤墒情节点常需在部署现场临时点亮指示灯、查询固件版本或切换采样周期，串口命令行正是最轻量的人机入口。这类接口的共性难题是：命令会不断增删，若把"解析—判断—执行"写成一条越来越长的 `if-else` 链，代码将迅速僵化。命令模式通过将"请求"封装为可查找、可调用的对象（在 C 语言中即**函数指针**），把命令的*注册*与*分发*彻底分离，使系统在不修改分发逻辑的前提下横向扩展。

**学习目标**

- 理解命令模式的**意图**与三大角色（Invoker/Command/Receiver），及其在裸机固件中的映射方式
- 掌握以**函数指针表**驱动命令分发的方法，说明其相对 `if-else`/`switch` 链的工程优势
- 实现一个带**缓冲区溢出防护**的串口命令行解析器，理解中断接收、环形缓冲与行组装的协作
- 在 STM32F103C8T6 + STM32CubeMX/CubeIDE 工程中完成设计、编码，并借助 PicSimLab 完成仿真验证

#### 2.6.1 命令模式原理

命令模式（Command Pattern）属于行为型设计模式，其核心意图是：**将一个请求封装为一个独立的对象，从而使发出请求的对象与执行请求的对象相互解耦。** 在面向对象语境中，这个"对象"是实现了统一接口的命令类；在资源受限的裸机 C 语言中，我们用一个**函数指针**加一段元数据（命令名、帮助文本）来充当同样的角色，既保留了解耦的收益，又避免了虚函数表的额外开销。

命令模式包含三个经典角色，它们在本节固件中的映射关系如下：

- **Invoker（调用者）**：只知道"要发出某个命令"，不关心命令由谁执行。本例中由行组装与分发逻辑 `cmd_process()` / `cmd_dispatch()` 承担。
- **Command（命令对象）**：封装了"做什么"的抽象接口。本例中即 `Command` 结构体——把命令名与处理函数指针绑定在一起。
- **Receiver（接收者）**：真正执行动作的实体。本例中为 `cmd_led()`、`cmd_help()`、`cmd_ver()` 等具体处理函数。

**从硬件字节流到动作执行的完整数据通路。** 一条命令从串口物理层进入，到最终驱动 LED，需要经过"中断接收→环形缓冲→行组装→查表分发→执行"五个阶段，如图 2-A 所示。该图的价值在于：它把上一节的生产者-消费者通道（前两级）与本节的命令分发机制（后三级）在同一张图中衔接起来，直观呈现二者的接力关系。

```bob

    │ "USART1 RX 中断"：收到 1 字节    │
```

图 2-A 中，中断只负责把单字节"生产"进环形缓冲，绝不在中断上下文中做解析——这正是 §2.5 强调的"ISR 尽量短"的实时性原则的延续。真正的解耦发生在最后两级：`cmd_dispatch()` 只依赖 `Command` 这一抽象接口去调用 `handler`，而不依赖任何具体的 LED 操作代码。

由图 2-B 可见，`Invoker` 与 `Receiver` 之间没有任何直接的编译期依赖，二者仅通过 `Command` 结构体中的函数指针间接相连。这意味着新增一条命令时，分发器 `cmd_dispatch()` 一行都不必改动，符合"对扩展开放、对修改封闭"的开闭原则。

**行组装子过程是一个显式状态机。** 图 2-A 的第三级"行组装"内部并非平凡的字符拷贝，而是一个需要处理边界的小状态机，如图 2-C 所示。其中 `RECV → OVERFLOW` 分支即缓冲区溢出防护的核心：当单行长度逼近 `CMD_LINE_MAX` 上限时，状态机不再写入缓冲区，而是置位溢出标志并持续丢弃字符，直至行结束符到来才统一报错复位，从根本上杜绝了数组越界写。

**为什么用函数指针表而非 if-else 链？** 这是本节的关键取舍，也是命令模式在 C 语言中最直接的体现。表 2-A 从多个工程维度对二者做了对比，帮助读者建立"何时该引入命令表"的判断标准。

**表 2-A** 函数指针表与 if-else/switch 链的多维对比
<!-- tbl:ch2-A 函数指针表与 if-else 链对比 -->

| 对比维度 | if-else / switch 链 | 函数指针表（命令模式） |
|----------|--------------------|------------------------|
| 新增命令 | 修改分发函数体，改动核心逻辑 | 仅在表中增加一行，分发逻辑零改动 |
| 可读性 | 命令增多后分支臃肿、难以速览 | 命令注册集中于一处，一目了然 |
| 耦合度 | 调用者直接依赖各具体实现 | 调用者仅依赖函数指针接口 |
| 运行时可变性 | 编译期固定，无法热替换 | 可在运行时替换表项，支持动态挂载 |
| 平均查找成本 | 顺序判断，最坏 $O(n)$ | 顺序查表 $O(n)$，可升级为哈希 $O(1)$ |
| 代码体积 | 分支指令随命令数线性膨胀 | 表项为只读数据，可置于 Flash 常量区 |

表 2-A 表明：命令数很少（两三条）时二者差异不大，但一旦命令集会持续演进——这正是调试接口、参数配置菜单的典型特征——函数指针表在可维护性与可扩展性上的优势将迅速拉开。下一节的示例程序即以此为设计基线。

下面从 `command.c` 摘录三段核心代码，逐段说明其设计意图与关键点，并对照 issue #91 提出的三条验收标准加以印证。

**（1）命令表定义——命令模式的落点。** 该段目的是用一张只读表把命令名、处理函数与帮助文本绑定在一起，这张表就是命令模式中"命令对象"的集合，也是后续查表分发的数据基础。

```c
static const Command cmd_table[] = {             /* 函数指针表：扩展命令只改表 */
    { "led",  cmd_led,  "led on|off|toggle" },
    { "help", cmd_help, "show commands" },
    { "ver",  cmd_ver,  "firmware version" },
};
#define CMD_COUNT (sizeof(cmd_table) / sizeof(cmd_table[0]))
```

**关键点解读**：`cmd_table` 以 `static const` 修饰，编译后位于 Flash 只读区，不占用宝贵的 RAM；`CMD_COUNT` 通过 `sizeof` 自动推导表长，增删命令时无需手工维护计数。新增命令的全部成本就是"写一个处理函数 + 在表里加一行"，分发逻辑完全不动——这直接对应**验收标准①：函数指针表查找逻辑清晰**，因为命令的注册与查找被收敛到同一张显式的表中。

**（2）查表分发——调用者与接收者的解耦点。** 该段目的是把一整行命令文本拆成参数数组，再遍历命令表按名字匹配，命中后经函数指针回调具体处理函数，是命令模式"解耦"收益的集中体现。

```c
static void cmd_dispatch(char *line) {           /* 解析参数并查表分发 */
    char *argv[CMD_ARGS_MAX]; int argc = 0;
    char *p = strtok(line, " ");
    while (p && argc < CMD_ARGS_MAX) { argv[argc++] = p; p = strtok(NULL, " "); }
    if (argc == 0) return;
    for (unsigned i = 0; i < CMD_COUNT; i++)     /* 查找逻辑：遍历命令表匹配名字 */
        if (!strcmp(argv[0], cmd_table[i].name)) { cmd_table[i].handler(argc, argv); return; }
    uart_puts("unknown command, type 'help'\r\n");
}
```

**关键点解读**：`strtok` 以空格切分出 `argv[0]`（命令名）与后续参数，`argc` 上限由 `CMD_ARGS_MAX` 约束以防参数数组越界；随后的 `for` 循环是整个命令模式的枢纽——它只认识 `Command` 接口，通过 `cmd_table[i].handler(argc, argv)` 间接调用，**完全不知道也不关心被调函数究竟是点灯还是打印版本**。匹配失败时给出友好提示而非静默丢弃。该段完整实现了从原始文本到具体动作的解析—分发链路，对应**验收标准②：串口命令解析器完整且支持多命令**。

**（3）行组装与溢出防护——健壮性的底线。** 该段目的是从环形缓冲逐字节取数、拼装成完整命令行，并在此过程中对超长输入实施防护，确保任何异常输入都不会破坏内存。

```c
void cmd_process(void) {
    static char line[CMD_LINE_MAX];
    static uint16_t idx = 0;
    static uint8_t  overflow = 0;                /* 溢出标志 */
    uint8_t c;
    while (rb_get(&c)) {
        if (c == '\r' || c == '\n') {
            if (overflow) { uart_puts("line too long\r\n"); }
            else if (idx > 0) { line[idx] = '\0'; cmd_dispatch(line); }
            idx = 0; overflow = 0;               /* 复位行状态 */
        } else if (idx < CMD_LINE_MAX - 1) {
            line[idx++] = (char)c;               /* 正常收字符 */
        } else {
            overflow = 1;                        /* 超长：置位并丢弃，杜绝越界写 */
        }
    }
}
```

**关键点解读**：写入条件被严格限制为 `idx < CMD_LINE_MAX - 1`，为字符串终止符 `'\0'` 预留了最后一个字节；一旦达到上限便进入 `else` 分支置位 `overflow` 并持续丢弃字符，绝不再向 `line[]` 写入，因此**无论输入多长都不可能发生数组越界写**。等到行结束符到来时，若 `overflow` 已置位则统一报 `line too long` 并复位，把错误处理与正常路径清晰分离。这正是对应图 2-C 状态机的 `OVERFLOW` 分支，落实了**验收标准③：缓冲区溢出防护**。此外，`cmd_process()` 在主循环前台运行、只做非阻塞的"取一个算一个"，与中断里的 `cmd_rx_feed()` 恰好构成 §2.5 的单生产者-单消费者关系，无需加锁即可安全共享环形缓冲。

#### 2.6.3 PicSimLab 仿真

为在无实体开发板的条件下验证固件行为，本节采用 PicSimLab（开源单片机仿真器）配合仓库自带的 `stm32_picsimlab_dev` Docker 容器进行仿真。该容器内置 PicSimLab 与 noVNC，可在浏览器中观察 STM32 Blue Pill 虚拟板的运行状态并与虚拟串口交互。

**接线与配置**：在 PicSimLab 中选择 STM32 Blue Pill（STM32F103C8）开发板；USART1（PA9/PA10）经容器内的虚拟串口桥接至主机，PC13 连接板载 LED 用于观察点灯效果。串口参数须与固件一致：115200 波特率、8 数据位、无校验、1 停止位（8N1）。

**命令行启动步骤**：仿真环境以 Docker Compose 一键拉起，全过程通过命令行完成，无需图形化配置：

```bash
# 1. 进入仿真容器目录并后台启动容器
cd code_examples/stm32_picsimlab_dev
docker compose up -d

# 2. 将交叉编译产物 firmware.bin 加载进仿真器
./run-firmware.sh ../exam2/4250705024_zhangqichuan_command_pattern/firmware.bin

# 3. 浏览器打开 noVNC 界面观察运行效果
#    地址：http://127.0.0.1:6080
```

> **注意**：`firmware.bin` 由工程内 `Makefile` 经 `arm-none-eabi-gcc` 在容器中交叉编译得到，属编译产物，已被 `.gitignore` 排除、不纳入版本库；仿真前需先在本地或容器内执行 `make` 生成。

#### 2.6.4 本章小结

本节以一个可运行的串口命令行为载体，系统讲解了命令模式在嵌入式固件中的落地方法。核心结论可凝练为三点：

- **以函数指针表替代 if-else 链**，把命令的注册与分发解耦，使系统"对扩展开放、对修改封闭"——新增命令只需增表项，分发逻辑零改动（表 2-A、验收标准①②）。
- **命令模式与生产者-消费者协同**：中断在环形缓冲端"生产"字节，主循环 `cmd_process()` 在消费端组装并分发命令，二者构成无锁的单生产者-单消费者关系，是 §2.5 数据通道的自然延伸（图 2-A）。
- **健壮性来自显式的边界处理**：行组装状态机以 `overflow` 标志实施缓冲区溢出防护，任何超长输入都不会破坏内存（图 2-C、验收标准③）。

命令模式与 §2.5 的生产者-消费者模式共同构成了事件驱动固件的骨架：前者解决"动作如何调度"，后者解决"数据如何流动"。这一"数据通道 + 命令分发"的组合，也为第 3 章外设驱动的命令化封装（如把传感器采样、执行器控制统一注册为命令）提供了直接的结构基础。在农业物联网终端中，这样一套轻量命令行既是现场调试的入口，也可平滑演进为远程运维的指令解析层。

#### 2.6.5 思考题

1. 若需支持带数值参数的命令（如 `pwm 50` 设置占空比为 50%），`cmd_dispatch()` 与 `cmd_led()` 一类处理函数需如何扩展？其中的字符串到整数转换应在哪一层完成，为什么？
2. 环形缓冲大小 `CMD_RB_SIZE` 被要求是 2 的幂，代码中用 `(idx + 1) & (SIZE - 1)` 代替取模运算。请说明这一写法为何等价于取模，以及它相对 `%` 运算在 Cortex-M3 上的性能意义。
3. 固件在中断中仅调用 `cmd_rx_feed()` 入队、把解析放到主循环，而没有在中断里直接解析命令。这一取舍体现了哪条实时性设计原则？若把解析搬进中断会带来什么风险？
4. 当命令数量增长到数十条时，`cmd_dispatch()` 的顺序查表为 $O(n)$。请设计一种将查找降为近似 $O(1)$ 的改进方案，并讨论其在 Flash/RAM 占用上的代价。
